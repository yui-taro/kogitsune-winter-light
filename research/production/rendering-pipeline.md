# 実装方式: 3D制作 → 2.5Dゲーム

## 再現可能な最小工程

1. **対象を固定:** PC、1920×1080を基準画面、境内1区画。右下に常設の4ボタンを置き、狐・狛犬・灯籠を初期画面に入れる。16:10と小さなウィンドウでもHUDとプレイ対象が重ならないか確認する。
2. **Blenderの共通設定:** 正投影の斜めカメラ、焦点距離に依存しない画面スケール、同じ色管理、同じカメラ角度と照明の基準を場面ファイルに共有する。背景・キャラ・遮蔽物は同じ画面座標へ投影する。正投影はこの作品の設計選択。
3. **背景:** 奥景、雪の地面、前景遮蔽物、灯籠点灯時／消灯時、遮蔽マスクを別に出力。地面と当たり判定・隠れ判定は同じ設計図から作る。Blenderにはレンダーパスとオブジェクト分離手段がある。[Blender Passes](https://docs.blender.org/manual/en/latest/render/layers/passes.html)。
4. **キャラ:** 子狐と狛犬を同じ正投影カメラ・光のもとでPNG RGBA連番として出力。まず4方向×待機／歩き／伏せだけ。全方向・全動作を先に量産しない。連番の方が途中失敗から再開しやすい。[Blender出力設定](https://docs.blender.org/manual/en/5.2/render/output/properties/output.html)、[透明フィルム](https://docs.blender.org/manual/en/latest/render/eevee/render_settings/film.html)。
5. **書き出し検査:** 各フレームに行動名、向き、フレーム番号、同じ足元ピボット、フレーム時間を付ける。背景を透明にした時に毛先が黒／白く縁取られないか、暗い雪と明るい雪の両方へ合成して見る。フレーム欠落・サイズずれ・アルファ欠落をPythonで検査する。
6. **raylib再生:** CMakeでバージョンを固定したraylibを取得し、C++ターゲットにリンク。背景、足跡、キャラ、前景、照明・雪の粒、HUDの順で描画する。raylibは部分テクスチャ描画、RenderTexture、ブレンドモード、シェーダーを備える。[raylibチートシート](https://www.raylib.com/cheatsheet/cheatsheet.html)、[公式CMake雛形](https://github.com/raysan5/raylib-game-template/blob/main/CMakeLists.txt)。

## 座標と重なりの契約

- **世界座標:** 雪面の2D平面を `(x,y)`、高さを別値とする。狐・狛犬・灯籠は「地面に接する点」を基準に位置決めする。
- **スクリーン座標:** Blenderで決めた正投影変換と同じ写像をゲーム側に持つ。画面上の足元は背景に焼き込んだ地面座標と一致させる。背景画像だけを別倍率で変形しない。
- **写像の実装:** 境内の既知の地面3点をBlender画像の画素へ投影し、2Dアフィン写像 `screen = origin + x * axis_x + y * axis_y` の係数を輸出する。ゲームはその係数で狐、足跡、灯籠、当たり判定表示を同じ位置へ置く。カメラや背景解像度を変えた時は係数を再輸出する。
- **カメラ:** まず1区画は完全固定。追尾は背景全体と全スプライトを同じ量だけ平行移動する場合に限る。自由回転・大ズームを導入するならこの素材方式を再評価する。
- **描画順:** 地面に接する点の画面奥行きでキャラ／足跡／小物を並べ、鳥居・木・倒木は前景と奥景に分割。1枚の背景画像だけでは「柱の前後を通る」を表現できない。
- **衝突:** 見た目の足元と当たり判定を一致させる。耳や尾の画像範囲で衝突しない。隠れられる物には遮蔽領域と視線遮断領域を明示する。
- **影:** 透明キャラ画像に長い地面影を焼き込むと移動や灯籠の光と衝突する。まず足元の短い接地影を独立した画像として描き、長い影は境内の固定背景側に限定する。

素材manifestの最小例。数値は形式例で、実際の座標や長さではない。

```json
{
  "fox.walk.ne": {
    "atlas": "fox_walk_ne.png",
    "frames": 8,
    "fps": 12,
    "pivot_px": [96, 170],
    "world_foot_offset": [0, 0]
  }
}
```

`pivot_px`は全フレームで同じ足元の画像内位置を示す。足を上げるアニメでも、世界座標の基準は跳ねさせない。UI素材はキャラアトラスから分離し、解像度変更時に独立して調整できるようにする。

素材量は`幅×高さ×4バイト×フレーム数`でまず**展開後メモリの上限目安**を計算する。例として256×256のRGBAを8フレーム×4方向×6行動持つと、約48 MiB／キャラ（アトラスの余白・別レイヤーは除く）。512×512なら約192 MiB。ディスクのPNGサイズだけで判断せず、GPUテクスチャの最大寸法、VRAM使用量、読み込み時間を試作機で測る。数字は設計上の計算で、実機計測値ではない。

## 難所別の具体策

| 難所 | 試作で採る方法 | 合格しなければ |
| --- | --- | --- |
| 灯籠を持って移動した時の光 | 点灯／消灯の背景を用意。狐の周辺に地面の柔らかな光だまり、狐と近い遮蔽物に暖色の別レイヤーを合成 | 地面や遮蔽物の不整合が目立つなら、その場面の描画をリアルタイム3Dで試す |
| 雪の足跡 | 世界座標で左右交互にデカールを置く。新旧の違いは濃淡・輪郭で表し、尾で払うと消えるアニメを重ねる | 描画順・足の接地がずれる場合は投影とピボットを修正 |
| 方向転換 | 4方向で開始し、向きを変えた瞬間に足が跳ねないようピボットを固定 | 斜め移動が読めない時だけ8方向に拡張 |
| 毛と透明縁 | alpha付き連番を実背景へ合成し、毛先の輪郭を確認 | 毛束の太さ、透過設定、アトラスの余白と拡張色を調整 |
| アトラスの容量 | 行動単位で分け、実表示サイズとVRAM・ロード時間を記録 | 対象方向・fps・解像度を削る。重要な近景は別の高解像度素材にする |
| HUD | 入力状態とゲーム状態を分離し、四つのボタンの位置を常時固定 | 使えない理由・キー表示・対象名の出し方を修正 |

灯籠の光は「物理照明の完全再現」ではなく、見た目とゲーム内の可視性が一致する演出として設計する。灯籠が離れると神社が暗くなるという物語上の変化を見せる。品質は実際の動画で判定する。

## 最初の垂直スライス

静止画 → 狐の歩行・伏せ → 足跡を残す／消す → 柱の前後を通る → 灯籠を拾う・置く → 灯籠移動中の光 → 狛犬のローカル行動 → Jevへの差し替え。この順なら、美術方式が不成立だった時の手戻りを境内1区画に限れる。合否は[validation.md](validation.md)。

**実装上の注意:** CMake雛形はCターゲットなので、実装時にC++ターゲットへ変更する。ネットワークHTTPはraylibの責務に含めず、ゲーム側に独立したクライアント層を置く。PythonはBlender・素材変換用。リアルタイムの操作と描画はC++で保持する。
