# 『こぎつねと冬の灯り』画面・UI・実装方式の検討

版: 0.1／2026-10-04。対象は[ストーリー設計書](fox-story-design.md)の短編。**PC向け、斜め見下ろしの固定視点、子狐と狛犬を高品質な3Dモデルで制作**する前提の提案。対象機種と作業人数は未確定なので、実機検証前の方式決定である。

## 結論

**Blenderで3Dモデルと舞台を制作し、固定カメラから背景・キャラクターアニメーションを高品質にレンダリングする。ゲーム本体はC++ + raylibで2.5Dとして動かす。** 美術の仕上げをBlender側に集中し、ゲーム側は移動、足跡、狛犬の判断、灯籠の光の演出、常設UIを担当する。

これは子狐の毛並み、石の狛犬、雪と灯りの陰影を見せつつ、広いリアルタイム3D世界を制作しないための選択。**画質が自動的に上がる方式ではない。** 3Dモデル、リグ、アニメーション、背景の構図は制作が必要。視点を固定することで、見える面と演出に作業を集中する。

Blenderはアニメーションを画像連番として出力でき、透明背景やレンダーパスを使って素材を分けられる。[Blenderの出力](https://docs.blender.org/manual/en/5.2/render/output/properties/output.html)・[透明フィルム](https://docs.blender.org/manual/en/latest/render/eevee/render_settings/film.html)・[レンダーパス](https://docs.blender.org/manual/en/dev/render/layers/passes.html)。raylibには2D描画、シェーダー、レンダー先テクスチャ、音、入力の機能がある一方、シーン編集用の統合エディタはない。[raylib公式](https://www.raylib.com/)・[例集](https://www.raylib.com/examples.html)。

## 方式比較

| 方式 | 得られるもの | この作品での負担 | 判断 |
| --- | --- | --- | --- |
| リアルタイム3D（C++ + Unrealなど） | 自由な視点、動く灯籠による立体的な光と影、連続したキャラ演技 | 全エリアの見える面、3Dレベル、描画設定、カメラ、最適化を作り込む必要がある | 自由視点や物理的な光を作品の中心にする場合の候補 |
| **Blenderで作った画を使う固定視点2.5D** | 高品質な3Dモデルと背景を、決めた構図で見せやすい。小さな舞台へ美術作業を集中できる | 方向別アニメーション、前後関係、動く灯籠の光を2Dで設計する必要がある | **本作の第一候補** |
| 手描き2D中心 | 絵本の個性を出しやすい。動きの設計がシンプル | 3Dモデルの出来をゲーム画面で直接見せにくい。手描きアニメーション量が増える | ビジュアル方針が手描きに変わる場合の候補 |

Python + Panda3DやJava + libGDXでも制作は可能。言語だけで絵の品質は決まらない。今回の第一候補はC++ + raylibだが、Javaに慣れているなら**同じ素材方式をJava + libGDX**で実装できる。libGDXには2Dスプライト描画、レンダー先テクスチャ、レイアウト可能なUIがある。[SpriteBatch](https://libgdx.com/wiki/graphics/2d/spritebatch-textureregions-and-sprites)・[FrameBuffer](https://libgdx.com/wiki/graphics/opengl-utils/frame-buffer-objects)・[Scene2d.ui](https://libgdx.com/wiki/graphics/2d/scene2d/scene2d-ui)。PythonはBlenderの書き出し自動化や小さな検証ツールに使う想定。

## 画面の完成像

**画風:** 写実一辺倒ではなく、「立体のある絵本映画」。子狐は柔らかな毛並みと大きな尾、狛犬は雪をかぶった石肌とひびの中の橙の光。背景は青い夜の杉林、朱の鳥居、金色の灯籠。画面全体の細部より、狐・狛犬・灯籠の三つが一目で読めることを優先する。

**ゲーム中のカメラ:** 斜め見下ろしの角度をエリアごとに固定し、緩やかに追尾する。プレイヤーがカメラを回す操作は用意しない。重要物は中央からやや左に置き、右下にUIの余白を確保する。神社の境内では灯籠と狛犬が同時に見える構図を優先する。

**見せ場のアップ:** 通常画面では狐の毛並みや狛犬の細かな表情が見えにくい。そのため、巣の冒頭、狛犬の初登場、灯籠をくわえる瞬間、火を分ける結末に、同じ3Dモデルを使った短い別カメラのレンダーを入れる。モデル品質を物語の見せ場で確実に見せる。

## 右下に常設する行動UI

ゲームプレイ中、右下に**位置が変わらない四つのボタン**を2×2で置く。狐ができることをアイコンと短い文字で示し、使えない場面でも消さずに薄く表示する。操作できない演出場面だけ薄くフェードする。

```text
┌──────────────────────── ゲーム画面 ────────────────────────┐
│  巣／森／鳥居／境内                         神社の灯り       │
│          子狐 ← 足跡                    狛犬                │
│                                                            │
│                                       ┌────────┬────────┐  │
│                                       │  伏せる │   走る  │  │
│                                       ├────────┼────────┤  │
│                                       │ 尾で払う│  触れる │  │
│                                       └────────┴────────┘  │
└────────────────────────────────────────────────────────────┘
```

| 固定位置のボタン | 役割 | 利用可否・変化 |
| --- | --- | --- |
| **伏せる** | 体を低くして視線を避け、狭い下をくぐる | 常時表示。場所に応じて効果を示す。 |
| **走る** | 速く移動するが足音と足跡が目立つ | 常時表示。灯籠をくわえている間は速度と音が変わる。 |
| **尾で払う** | 近くの新しい足跡を雪でならす | 跡がない場所では薄く表示し、なぜ使えないか短く示す。 |
| **触れる** | 近くの物に働きかける | 鈴なら「鳴らす」、灯籠なら「くわえる」、運搬中は「置く」に表示が変わる。ボタン位置は固定。 |

ボタンの絵は木彫りのお守りのような輪郭にし、背景を隠す大きな不透明パネルは避ける。使用可能は金の縁と明確な形、使用不可は灰色と斜線など**色以外でも識別**できるようにする。マウス・キーボード・ゲームパッドを同じアクションに割り当て、ボタン内のキー表示だけ入力機器に合わせて変える。16:9と16:10で最初から配置を確認する。

「触れる」の対象は狐の近くに小さな印を出す。対象が二つ重なる場合は狙っている対象名を表示し、勝手に灯籠を拾わない。開始時から四つとも見せ、冒頭の森で一つずつ使い方を体験させる。

PCの初期操作案は `WASD` 移動、`Ctrl` 伏せる、`Shift` 走る、`Q` 尾で払う、`E` 触れる。右下の各ボタンはマウスでも押せる。ゲームパッドでは左スティック移動と四つの対応ボタンを使い、表示するキー名を自動で切り替える。割り当ては操作試作で確定する。

## 素材の作り方と描画順

1. **Blender原本:** 巣・森・境内を3Dで作り、場面ごとに固定カメラと共通の色設定を決める。子狐・弟妹・狛犬も同じ制作環境でモデリング、リグ、アニメーションする。
2. **背景を分けて描き出す:** 雪の地面、遠景、遮蔽物の手前部分、神社の灯りがある／ない状態、場面別の影を別の画像として出す。鳥居の柱や倒木がキャラの前に来る位置を明示する。
3. **キャラを透明背景で書き出す:** 子狐と狛犬の待機・歩行・走行・伏せ・振り向き・くわえる等を、必要な方向ごとに画像連番へ。最初は4方向で試し、動きが粗く見える場合のみ方向を増やす。Pythonの書き出しスクリプトで同じカメラ・光・大きさを保つ。
4. **ゲームで重ねる:** 背景 → 既存の足跡 → キャラと遮蔽物を奥行き順に配置 → 雪と灯籠の光 → UI。雪の粒は画面の手前と奥に分ける。狛犬の視線や耳はアニメーションで読ませる。
5. **特別な絵:** 冒頭と結末の近景は別カメラで高解像度レンダーし、短い画像連番または映像として再生する。通常プレイのキャラを無理に拡大しない。

### この方式の難所と対策

- **動く灯籠の光:** 神社の静止した灯りと盗難後の暗い神社は別の背景として作る。子狐が運ぶ光は2Dの柔らかな照明マスク、子狐・雪・近くの遮蔽物への色変化で表現する。物理的に正しい影を全位置で再現する設計にはしない。1部屋の映像試作で違和感を必ず確認する。
- **キャラが物の前後を通る:** 鳥居、杉、倒木を手前・奥に分ける。隠れられる場所の表示と当たり判定を一致させる。複雑な重なりを増やし過ぎない。
- **アニメーション量:** 方向と行動の組合せが増えるため、狐と狛犬の基本移動・伏せ・灯籠保持を先に揃える。物語で使わない動作を量産しない。画像サイズとメモリは実際の表示サイズで測る。
- **カメラ自由度:** 場面中の回転と大きなズームはできない前提でレベルを設計する。隠れ道の奥行きが読めない場合は構図か場面の切り方を直す。

## ゲームの中身の分担

| 部分 | 実装する内容 |
| --- | --- |
| **C++ + raylibのゲーム本体** | 入力、固定視点の描画とUI、狐の操作、当たり判定、足跡の生成と消去、視界と音、狛犬の移動、灯籠の所持、セーブ、演出再生。 |
| **Jevとの接続** | 狛犬が新しい手掛かりを見た時に、知っている情報と性格から短い行動候補を選ぶ。プレイ中の滑らかな移動はローカルで続ける。[Choiceの仕様](https://docs.typesafe.ai/primitives/choice)。 |
| **小さな中継サーバー** | APIキーを保持してJevを呼び、期限切れ・呼び出し数を管理する。公開配布を想定する場合にゲーム本体へキーを埋め込まない。 |
| **Pythonの制作ツール** | Blenderから背景・方向別アニメーション・遮蔽マスクを一括書き出しし、素材の寸法や欠落を検査する。 |
| **Blenderの素材原本** | モデル、毛・石・雪の材質、アニメーション、背景、カメラ、照明。 |

Jevが遅い時は狛犬が直前の行動を短時間続けるか、灯籠を守るローカル方針に戻す。足跡を見つけた瞬間などに呼び、毎秒の固定呼び出しを前提にしない。狛犬の視界にない狐の座標は入力へ含めない。[JevのState](https://docs.typesafe.ai/concepts/state)は構造化した状態を受け取れるが、性格の一貫性と判断品質は自作場面で確認が必要。

## 先に作る実証シーン

**「灯籠のある境内」1画面**だけを最初に完成品質に近づける。雪の地面、朱の鳥居、灯籠、子狐、狛犬、右下の四つのボタンを入れる。子狐が足跡を残す／尾で消す、鈴を鳴らす、灯籠をくわえる、神社が暗くなる、狛犬が別の行動を選ぶところまで通す。

確認する順番:

1. **一枚絵:** 狐・狛犬・灯籠が背景から埋もれず、目標と危険が一目で分かるか。
2. **10秒の操作:** 狐の方向転換とアニメーションが滑らかか。右下のボタンが読めて邪魔にならないか。
3. **足跡と遮蔽:** 追跡の手掛かりが見え、鳥居や倒木の前後が自然か。
4. **灯籠を持った映像:** 動く光、狐の毛、石の狛犬、雪の色が同じ世界に見えるか。ここで違和感が強ければリアルタイム3Dへ方式変更を検討する。
5. **Jevの判断:** 同じ盤面を固定ルール版と比較し、狛犬の慎重さと状況への反応が見えるか。これは絵の検証とは分けて測る。

**本番の制作方式を決めるゲートは4まで。** 1部屋で絵の統一感が成立してから、森や巣の素材を増やす。映像品質が未確認のまま全編をこの方式で量産しない。
