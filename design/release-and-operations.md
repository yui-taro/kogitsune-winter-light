# 『こぎつねと冬の灯り』公開・運用設計書

版: 0.1／2026-10-04  
状態: **レビュー用草案。GitHubリポジトリ、Windows実行版、Jev中継先の公開・運用はまだ行っていない。接続方式・費用負担・素材ライセンスの最終判断が必要。**

## 1. 公開の範囲と前提

ユーザー決定済みの公開物は**GitHub上のソースコードとWindows実行版**（D-08）。完成版はプレイ中のJev接続を必要とし、短い切断には一時的な代替行動を使う（D-03）。ゲーム本体、素材、接続先の構成は[基本設計](basic-design.md)、[技術・素材設計](technical-and-assets.md)、[狛犬・Jev仕様](komainu-jev.md)に従う。

この作業場には現在、企画・画像・設計文書だけがあり、制作コードとWindowsビルドはない。GitHubの公開先、リポジトリのライセンス、中継先の運営者も未決定。**本書の完成は公開許可や公開作業の開始を意味しない。**

| 対象 | 公開時に用意するもの | 未決定の範囲 |
| --- | --- | --- |
| ソースリポジトリ | ゲーム・中継の公開可能なソース、ビルド手順、操作・接続説明、依存物と素材の権利表示 | ソースのライセンス、Blender原本・生成指示・設定画像・中継実装の公開範囲 |
| Windows実行版 | 実行ファイル、必要な完成素材、必要な依存物の告知、操作・接続・障害時の説明 | 対象Windows版、最低スペック、インストーラーかZIPか、署名の有無 |
| Jev接続先 | 秘密鍵を保持する中継、API利用量と障害の監視、認証・利用制限 | ホスト、誰が費用を負担するか、公開ユーザーの認証と濫用対策 |
| 権利台帳 | コード・素材・音・フォント・依存物の出典、権利者、利用条件、配布可否 | D-13の最終的なライセンスと公開素材の範囲 |

GitHubはリリースに実行ファイルなどのアセットを添付できる。[GitHub Releasesの公式手順](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)を参照し、公開直前にドラフトへ一式をそろえて確認する。リポジトリが公開であることだけでは第三者の再利用条件は明確にならないため、コードと素材の許諾条件を明記する。[GitHubのライセンス案内](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)。

## 2. 配布物の構成案

```text
repository/
  README.md                 # 作品、ビルド、操作、接続条件
  LICENSE                   # ソースの許諾条件（選定後）
  NOTICE / THIRD_PARTY.md   # 依存物と素材の表示（必要な場合）
  game/                     # 公開対象としたソース
  server/                   # 公開対象とした中継ソース。秘密設定は含めない
  design/                   # 公開範囲を決めてから収録

release-<version>-windows.zip
  game.exe
  assets/                   # 実行に必要で配布権を確認した素材
  README.txt                # 起動、入力、接続、障害時の再試行
  THIRD_PARTY.txt           # 同梱物の表示
```

上記は構成案で、現物のフォルダではない。製品のソースを公開しても、制作途中の参照画像・Blender原本・生成指示・未採用画像を同じ範囲で公開するとは限らない。逆に、Windows実行版に必要な完成素材は配布可能な権利を確認しないと同梱できない。公開対象と除外対象をファイル単位の台帳で確認する。

**配布説明の必須項目:** 対応Windows環境、起動手順、`WASD`等の初期操作、オンライン接続必須、接続確認と再試行、短い通信障害での挙動、アプリ終了後の再開が可能か、問い合わせ先、版と更新履歴。APIキーやサーバー内部の設定値はユーザー向け説明へ記載しない。プレイ後の狛犬記録、ゲームパッド、近景などの追加候補は採用時だけ記載する。

## 3. Jev接続と秘密鍵

**第一候補:** 公開ゲーム → 専用中継先 → TypeSafe Jev API。ゲームが送るのは[狛犬仕様](komainu-jev.md)で定義した観測済み情報、合法候補、試行・判断ID。中継先がTypeSafeのAPIキーを秘密設定から読み、Choiceの応答をゲーム用契約に変換する。TypeSafeの[API仕様](https://docs.typesafe.ai/api)はBearer認証と`state`・`questions`を定めている。キーはゲームの実行ファイル、配布アーカイブ、公開リポジトリ、スクリーンショット、ログに入れない（N-06）。

| 境界 | 必要な防止策・確認 |
| --- | --- |
| ゲーム→中継 | 受け付ける場面・NPC・意図ID・状態項目・入力サイズを限定する。任意のTypeSafe質問や自由文を中継できる汎用プロキシにしない |
| 利用者の識別 | 公開クライアントに埋め込んだ共通秘密を認証の根拠にしない。認証方式、匿名プレイ可否、1利用者あたりの枠を公開方式と費用負担と一緒に決める |
| 中継→TypeSafe | APIキーを中継先だけで保持・更新し、モデル版・タイムアウト・再試行を固定して記録。鍵の漏えい時は失効・再発行できる手順を用意 |
| ゲームへの返答 | `attempt_id`・`decision_id`・`revision`を照合し、候補外・期限切れ・重複を拒否する。中継だけでなくゲーム本体でも検査 |
| 使用量 | 呼び出し件数と`usage.input_tokens`、失敗・再試行を集計。利用枠、費用通知、停止条件を運用者が決める |

**公開前に決める選択:** 中継先を誰が運営し、誰のTypeSafeアカウント・クレジットで支払い、プレイヤーをどう認証し、濫用や残高切れにどう対応するか。公開ソースから誰でも中継を呼べる構成であれば、配布前に利用制限を実測する。方式が決まらなければ、Jev接続必須のWindows版を「誰でもプレイ可能」として公開しない。[TypeSafeの利用条件](https://typesafe.ai/legal/mca)と実際の契約・Orderを、運用者が公開前に確認する。

## 4. 通信障害とプレイヤー案内

| 状況 | ゲーム内の扱い | 中継・運用側の扱い |
| --- | --- | --- |
| 起動時に接続不可 | 「接続が必要です」、再試行・タイトルへ戻る。Jevを使うプレイは始めない | 中継の到達性とTypeSafe認証を確認 |
| 一時的な遅延・切断 | 操作・描画は続け、狛犬は観測済み情報だけで安全なローカル行動を短く取る。控えめな「通信が不安定」表示 | 時間切れ、`429`、`529`、中継障害を分けて記録。無制限に再送しない |
| 長時間の障害 | 安全な地点で中断し「接続が必要です」と再試行方法を示す案。具体的な閾値と復元位置はD-09 | 障害を確認して公開状況に案内。復旧後は現行状態から新規判断を要求 |
| 認証失敗・利用枠不足 | 接続不能として案内し、ゲーム中に古い判断を採用しない | 鍵・契約・残高・利用枠を確認。必要なら鍵更新または運用停止 |
| 中継復旧 | プレイヤーを矛盾のない状態から再開。古い応答は実行しない | 新旧クライアント版と契約の互換を確認 |

`429`と`529`のバックオフは[TypeSafe公式API](https://docs.typesafe.ai/api)の案内に従う。プレイヤーにはHTTP番号を基本表示せず、何をすれば再開できるかを示す。長時間障害時のゲーム内閾値、セーブ／CPの復元、告知場所と連絡先は、接続方式と運用者が決まった時に[画面・操作仕様](ui-and-controls.md)と同じ文言で確定する。

## 5. データとログ

ゲームから外へ出す情報は狛犬の判断に必要なゲーム内の観測事実に限り、プレイヤーの氏名・メール・任意の入力文・端末内ファイルを`state`に含めない。中継ログには試行・判断ID、モデル版、結果分類、応答時間、入力トークン数、採用／破棄理由を残す。APIキー、認証トークン本文、不要な生の判断状態を記録しない。プレイヤー向けの狛犬記録を採用する場合はゲームが実際に保存した観測と意図だけを使う。

ログ保存場所・保存期間・閲覧者、利用者への説明文、障害時の問い合わせで受け取るデータは運用者決定後に確定する。TypeSafeへ送る内容と外部サービス側の取扱いは、公開時の[法務資料](https://docs.typesafe.ai/legal)と実際に適用される契約を確認する。実測ログを公開する場合も、秘密と利用者を識別できる情報を除く。

## 6. 素材と依存物の権利台帳

| 台帳項目 | 記録例・確認の観点 |
| --- | --- |
| 識別子と版 | C-01、C-05、P-01、E-01等の画像ID、3Dモデル、音、フォント、ライブラリ、採用版 |
| 作成元 | 自作、生成画像から人が確定した形、外部素材。参照元のURL・取得日・作者 |
| 使用条件 | 作品内利用、Windows実行版への同梱、ソースリポジトリでの公開、改変、再配布の可否 |
| 同梱表示 | 著作権表示、ライセンス本文、クレジット等の必要条件と配置先 |
| 判定 | 採用可／配布不可／追加確認、確認した人・日付、差し替え先 |

**優先して確認する素材:** 子狐・狛犬・灯籠・背景の完成モデルとテクスチャ、画像生成の基準画、音楽・効果音、フォント、raylibと他の依存物。新C-05は比較候補で最終採用前、U-01・U-02は画面検討用で完成HUD素材ではない。[画像一覧](image-reference-list.md)と[美術方針](art-and-audio.md)の採用状態を台帳へ反映する。

raylib等の依存物は**採用した固定版の**ライセンス本文を確認し、必要な表示を配布物・ソースに含める。[raylib公式リポジトリのライセンス](https://github.com/raysan5/raylib/blob/master/LICENSE)は参照先であり、採用版の確認に代えない。コードと完成素材で異なるライセンスを選ぶ場合は、リポジトリの`LICENSE`だけで全素材を許諾したように見えない配置と説明にする。ソースと素材の最終条件はD-13の判断事項。

## 7. 公開手順と差し戻し

1. **公開候補を固定:** ゲーム・中継契約、モデル版、素材manifest、Windowsビルド手順、ライセンス台帳、配布説明を一つの版にそろえる。
2. **検証ゲートを確認:** [検証・受け入れ計画](verification.md)のV0〜V6を通し、Windows実機でクリーン起動、操作・音・描画・接続・捕獲後の再挑戦を確認する。未測定の必須項目があれば公開判定を保留する。
3. **秘密と配布権を点検:** ソース履歴と配布アーカイブを検査し、鍵・トークン・私的設定・無許可素材がないことを確認する。発見時は単にファイルを消すだけでなく、鍵の失効や履歴・配布物の扱いを決める。
4. **GitHubのドラフトReleaseを作る:** 対象版、変更点、Windowsアセット、チェックサム、README・利用条件を添え、別のWindows PCでダウンロード物から起動する。GitHub公開の実行操作は別途ユーザーの指示に従う。
5. **公開後を監視:** 接続成功率、p50/p95、期限切れ判断、API使用量、連続失敗、利用枠、報告された起動・操作問題を確認する。実際のしきい値は試作データと運用者の費用判断で設定する。
6. **障害時の差し戻し:** 中継の新旧契約を混在させず、必要なら前版へ戻すか公開版の接続を停止する。プレイヤーには原因の詳細より、影響と再試行・更新の方法を先に知らせる。旧クライアントが接続できなくなる変更では更新案内を用意する。

公開したリリースには、どのモデル版・ゲーム版・中継契約版・素材版で検証したかを残す。後から`jev-latest`の指す版が変わって体験が変化しないよう、検証した固定モデル版を運用候補とする。[公式モデル一覧](https://docs.typesafe.ai/models)の公開値や利用条件は公開前・更新時に再確認する。
