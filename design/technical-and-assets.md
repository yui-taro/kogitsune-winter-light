# 『こぎつねと冬の灯り』技術・素材設計書

版: 0.1／2026-10-04  
状態: **レビュー用草案。技術は候補と採否条件を明記する。境内1画面の実装・映像・Windows実機での検証はまだ行っていない。**

## 1. 目的と採否の境界

本書は[基本設計](basic-design.md)と[画面・操作仕様](ui-and-controls.md)を実現する技術候補、地形・素材・書き出しの契約、ビルドと秘密情報の扱いを定める。画風「立体のある絵本映画」、Windows PC、キーボード・マウス、GitHubでのソースと実行版の公開は[要件](requirements.md)に従う。描画方式は動く灯籠の光が成立するまで確定しない。

| 層 | 第一候補 | 採用前に確認すること |
| --- | --- | --- |
| ゲーム本体 | C++とraylib。入力、ゲーム状態、衝突、感覚判定、アニメ再生、音・HUD、非同期通信の受け渡し | 対象Windowsで起動・描画・入力・音が成立し、品質・性能が満たせるか |
| 美術原本 | Blender。子狐・狛犬・灯籠・背景の3Dモデル、共通カメラと照明 | 新C-05の二形態が同じ一体として成立し、実画面で読めるか |
| 素材変換 | Pythonの書き出し・検査ツール。画像連番からアトラスとmanifestを作る案 | 同じ設定から再生成でき、欠損・ずれ・容量超過を検出できるか |
| 描画 | 固定斜めカメラのプリレンダー背景と透過アニメを2.5D合成 | 移動する灯籠の光、雪、毛、石、遮蔽物の前後が動画で自然か |
| Jev連携 | ゲームとは別の中継先。ゲームの観測済み状態と合法候補をJev Choiceへ変換 | 実APIの遅延・費用・認証・障害を測り、秘密鍵を配布物に入れず運用できるか |

Unityは使わないというユーザーの希望に従う。C++ + raylibとBlenderの組み合わせは[制作方式の調査](../research/production/README.md)の第一候補であり、採用済みの製品技術ではない。Pythonは素材処理の候補で、ゲームの毎フレーム処理を担当させない。中継先の実装言語、ホスト、認証方式は[公開・運用設計](release-and-operations.md)で決める。

## 2. 実装境界とデータの流れ

```text
Blender原本 ──同一カメラで出力──> 背景層・キャラ連番・遮蔽マスク
      │                                    │
      └──地形図・基準点──> 世界座標と投影係数 ──┐
                                                v
Python検査・アトラス化 ──> manifest + 実行用素材 ──> ゲーム本体
                                                    │
                           感覚判定 → 観測・記憶 → 合法候補
                                                    │
                                         中継先 → Jev Choice
                                                    │
                                鮮度検査 → 予兆・移動・描画
```

世界状態と[狛犬・Jev仕様](komainu-jev.md)の観測はゲーム本体が所有する。素材の絵やネットワーク応答は世界状態を直接書き換えず、ゲーム側が整合を確認してから適用する。ゲームから中継先への要求は`attempt_id`、`decision_id`、`revision`を含み、APIキーは中継先だけに置く。

## 3. 座標・地形・当たり判定

| 項目 | 契約（第一候補） |
| --- | --- |
| 世界座標 | 雪面を2Dの`(x, y)`、必要な高さを別値とする。狐・狛犬・灯籠は**地面への接地点**を位置の基準にする |
| 投影 | Blenderの固定斜め正投影カメラから、地面の既知の3点で`screen = origin + x × axis_x + y × axis_y`を出力する案。背景・足跡・キャラ・小道具で同じ係数を使う |
| カメラ移動 | 境内の最小試作では固定。場面内の追尾は背景・前景・キャラ・足跡を同じ量だけ平行移動する。回転や独立拡大はしない |
| 通行 | 狐の足元で衝突判定し、耳や尾の画像外形では判定しない。倒木は伏せると通れる狐の通路、山犬には通れない地形として定義する |
| 視線・遮蔽 | 見た目の柱・木・床下と、視線遮断領域を同じ地形図から定義する。狛犬が遮蔽越しの狐を見たことにしない |
| 聴覚 | 音源の世界座標と種類を正本にする。届く範囲・遮蔽・吹雪の影響をゲームが決め、同じ出来事の画面演出と音へ渡す |
| 足跡 | 世界座標に接地イベントから配置し、向き・生成時刻・消去を記録する。年齢や風による見た目と、狛犬に見える条件を同じ状態から計算する |

地形の正確な通行幅・座標・視界距離は、[レベル設計](story-and-levels.md)の模式図や生成画像から推測して確定しない。境内1画面の平面図を作り、鳥居と倒木の二つの出入口、台座、狛犬の定位置、社の床下、前景遮蔽物を寸法付きで配置する。通れる道と狛犬の合法な行き先が一致することを確認する。

## 4. 描画層と灯籠の光

**2.5D合成の第一候補:** 奥景 → 雪の地面 → 足跡 → 地面の短い接地影 → キャラ・小道具を足元の奥行き順 → 前景遮蔽物 → 灯籠の光と雪の前景粒子 → HUD。鳥居、杉、倒木は奥側と手前側を分ける。背景を1枚に焼き込んで、狐が柱の前後を通れなくなることを避ける。[描画工程の調査](../research/production/rendering-pipeline.md)。

台座上の灯籠には点灯・消灯の背景差分を用意する。狐がくわえた灯籠には地面の暖色の光だまり、狐と近い遮蔽物への反射を別レイヤーで合成する案。**狛犬の感覚判定に使う光の範囲とプレイヤーに見える光を一致させる。** S3で台座が暗くなり、S4で光が動く動画を見て、毛先・雪面・石・前景に破綻がないか確認する。不成立なら描画だけリアルタイム3Dへ切り替える検証を行い、ゲーム状態・UI・Jev契約は維持する。

絵本映画調の基準は[V-01 A案](v-01/a-storybook-3d.png)と[V-02](v-02/gameplay-v02.png)。V-02の旧狛犬は造形基準に使わず、新C-05の石像・山犬の設定画を最終照合してからモデル化する。音は鈴・足音・火・風を独立した役割で扱い、音量と画面上の位置が手掛かりの意味と矛盾しないようにする。

## 5. 素材の種類と命名契約

| 素材 | 原本・参照 | 実行用の候補 | 検査すること |
| --- | --- | --- | --- |
| 背景・前景 | 場面ごとのBlender原本。E-01〜E-04の採用候補を参照 | 奥景、雪面、前景、遮蔽マスク、灯籠の点灯／消灯差分 | 同じカメラ・色管理・画角、投影係数、アルファ、前後関係 |
| 狐 | C-01〜C-03の採用候補から人が比率を整理したモデル | 方向・行動別のRGBA連番／アトラス。まず4方向の待機・歩行・伏せ | 足元ピボット、方向転換、雪面の接地、毛先の透過縁 |
| 狛犬／山犬 | 新C-05とC-06を照合した一体の二形態モデル | 石の見張り・予兆・変化、山犬の調査・追跡・帰還 | 共通の印と比率、変化前後の位置、耳・目線の読みやすさ |
| 灯籠・小道具 | P-01、P-02。形の矛盾は3Dで決める | 台座、くわえる／地面に置く灯籠、鈴、赤い布、枝、足跡 | 点灯／消灯でも形が同じ、狐の口と狛犬の前足の接触 |
| UI・文字 | U-01・U-02は検討用画像。挙動は[画面・操作仕様](ui-and-controls.md) | 編集可能なアイコン、文字、ボタン枠。キャラアトラスから分離 | 小さい画面での可読性、色なしでの状態識別、キー表示 |
| 音 | 自作または利用条件を確認した原本 | 効果音・音楽の実行形式は実装時に選択 | 手掛かり音が風・音楽に埋もれないこと、音なしでも重要事象が読めること |

命名は`<対象>.<行動>.<向き>.<版>`のように機械で識別できる規則を使い、原本・中間出力・実行用の各段階で同じIDを維持する。方向名、フレーム時間、足元ピボット、対応するカメラ版、照明版、出典・利用条件をmanifestへ記録する。画像生成の比較候補をそのまま完成素材にせず、採用版・参照画像・プロンプト・3D化で確定した形を[画像一覧](image-reference-list.md)の記録に残す。

```json
{
  "asset_id": "fox.walk.ne.v1",
  "source_scene": "fox_character.blend",
  "camera_id": "courtyard_ortho_v1",
  "atlas": "fox_walk_ne_v1.png",
  "frames": 8,
  "fps": 12,
  "pivot_px": [96, 170],
  "projection_id": "courtyard_projection_v1"
}
```

上は**manifest形式の例**で、ファイル名・数値は採用済みではない。1フレームの欠落、ピボットずれ、アルファ欠落、異なるカメラ版の混入は変換時に失敗として検出する。暗い雪と明るい雪に同じフレームを置き、毛の白／黒い縁と影の浮きを見る。

## 6. 容量・性能・再現性

展開後のRGBA画像は概算で`幅 × 高さ × 4バイト × フレーム数`を使い、全キャラ・方向・動作の合計を見積もる。PNGのディスク容量だけで判断せず、GPU上のテクスチャ、アトラスの余白、読み込み時間を測る。4方向で始め、実画面で不足した時だけ方向数・解像度を増やす。近景に必要な高解像度素材は通常アニメと分離する。

| 測る値 | 測る場所 | 合否を決める時期 |
| --- | --- | --- |
| 起動時間、場面切替、展開後メモリ・VRAM | 境内1画面とWindows実機 | 対象PCと最低環境を決めた後 |
| フレーム時間、入力から動作開始まで | 歩行、足跡多数、灯籠運搬、吹雪、HUD表示 | [検証計画](verification.md)で目標を定めてから |
| 描画の一致 | 運ばれる光、遮蔽物の前後、足元、毛先 | 動画試作の採否ゲートで |
| 再生成の一致 | 同じBlender原本・カメラ・スクリプト・manifestで再出力 | 最初の素材変換時と公開前 |

ライブラリ・Blender・CMake・コンパイラの版を、環境ゲート通過時に固定して記録する。現在の調査時点では、このMacでBlender・CMake・raylibの連結動作を確認していない（[実証計画](../research/production/validation.md)）。対象Windowsの版、最低スペック、画面サイズ、フレームレートの数値目標は未決定で、実機を決めてから設定する（N-02、N-08）。

## 7. ビルド・配布物・秘密情報

**フォルダ構成案（実装開始時に作る）:** `art/blender/`に原本、`art/exports/`に中間素材、`tools/`に変換・検査、`game/src/`にC++本体、`game/assets/`に実行用素材、`server/`に中継、`tests/fixtures/`に固定盤面を置く。現段階で空フォルダや制作コードは追加しない。

- CMakeでゲーム本体をC++ターゲットとしてビルドする案。raylibと他の依存物は採用した版を固定し、Windowsでクリーンビルドできる手順を残す。raylibの実際に使う描画・音・入力APIは[公式チートシート](https://www.raylib.com/cheatsheet/cheatsheet.html)で実装時に再確認する。
- Windows実行版は、起動に必要な実行ファイル、採用した素材、依存物の告知、操作・接続の説明を一式にする。開発用のBlender原本や比較画像を同梱するかは別途決める。
- TypeSafe APIキーはゲームのソース・manifest・設定画像・実行ファイル・ログに含めない。中継先の秘密設定で保持し、ゲームは期限と認証を持つ専用契約を使う案。中継先の不正利用防止と費用負担を決めるまで公開接続を成立したとみなさない。
- 依存ライブラリ、音、フォント、参考画像、生成画像、完成モデルの出典・利用条件を素材台帳で追い、公開する範囲とライセンスを[公開・運用設計](release-and-operations.md)で確定する。

## 8. 採用ゲートと残る判断

1. **環境:** Blenderの出力とWindowsの最小ウィンドウを再現できる。版、コマンド、実行ログを残す。
2. **画面:** 境内1画面に子狐・二形態の守り手・灯籠・足跡・右下HUDを同じ画角で置く。縮小しても目標と危険が読める。
3. **動作と光:** 狐の歩行・伏せ・足跡消し、柱の前後、盗難、運搬中の光を動画で確認する。光が成立しなければリアルタイム3D案と同じ場面で比較する。
4. **Jev:** モックで契約と古い応答の破棄を確認後、実APIの固定盤面で遅延・費用・判断品質を測る。結果は`komainu-jev.md`と`verification.md`へ戻す。
5. **Windowsと配布:** 対象実機でクリーンビルド・起動・入力・音・接続を確認し、配布物から鍵と不要な原本が見つからないことを確認する。

採用可否を判断する基準と記録形式は[検証・受け入れ計画](verification.md)に定める。モデルの寸法、アトラスの容量上限、Windowsの最低仕様、サーバーの方式はこのゲートの結果を見て改訂する。
