## 1. 作品の目的

子狐が大切なものをこっそり持ち帰る**巣から神社までの短編ゲーム**を作る。**愛らしいキャラクターと完成度の高い見た目**で世界観を伝え、狛犬が見聞きしたことと性格に応じて行動を変えることで、プレイヤーに「この相手は状況を考えている」と感じてもらう。Jevの利用そのものを説明するより、遊びの中でその価値が分かることを目指す。

企画中の物語は、吹雪で壊れた巣にいる弟妹を温めるため、子狐が神社の灯籠を持ち出す『こぎつねと冬の灯り』。[物語案](../research/fox-story-design.md)には、巣・森・鳥居・境内・帰路・結末までの進行がある。細部は本書で確定するまで変更可能。

### 成功とみなす体験（評価目標）

| ID | プレイヤー体験 | 確認方法の案 |
| --- | --- | --- |
| E-01 | 冒頭で「誰のために、何を取りに行くか」が伝わる | 初見の人に短い冒頭映像を見てもらい、自分の言葉で説明できるか確認する |
| E-02 | 子狐を操作したい、守りたいと感じる | 実際のゲーム画面サイズで表情・動き・シルエットを見てもらう |
| E-03 | 狛犬の行動に驚きがあり、直前の手掛かりから納得できる | プレイ後に「なぜ動いたと思うか」を聞き、追跡記録と照合する |
| E-04 | AI判断の違いが攻略に影響する | 同じ盤面で固定ルール版とJev版を比較し、プレイヤーが違いを説明できるか確認する |
| E-05 | 雪・灯り・神社・キャラクターが一つの世界に見える | 完成品質に近い境内1画面を実際の表示サイズで評価する |

数値の合格ラインや評価人数は未決定。これらは制作時の受け入れ条件を決めるための土台であり、実証済みの成果ではない。

### 想定する価値の見せ場（提案）

1. **最初の遭遇:** 狛犬は鈴だけで無条件に動かず、狐が残した足跡や灯籠との距離も見て判断する。慎重さが行動で分かる。
2. **工作の変化:** 狛犬が実際に空振りした囮を記憶し、同じ工作に対する反応が変わる。狐の工夫が攻略に影響する。
3. **盗難後:** 灯籠の光と新しい足跡を見て、追跡・出口警戒などから選ぶ。帰り道が往路とは違う遊びになる。

これらはゲーム体験の設計仮説であり、Jevの応答だけで成立が保証されるものではない。ゲームルール、演技、プレイヤーへの情報提示を合わせて検証する。

## 3. プレイの範囲（提案）

**完成版の体験範囲:** 子狐が巣を出て森と鳥居を通り、神社で狛犬の注意をかわして灯籠を取り、巣へ戻る。行きは足跡、帰りは持ち運ぶ灯りが危険になる。[場面構成の根拠](../research/fox-story-design.md)。総プレイ時間は未決定だが、**開始後5〜10分以内に、狛犬のJev判断が映える最初の場面へ到達する**。この時点で灯籠を盗み終える必要はない。

最初の検証単位は境内1画面、子狐1匹、狛犬1体、灯籠1つ。ここで遊び・AI・見た目が成立するかを確かめた後、巣から神社までの全編へ広げる。これは**制作順の提案**であり、完成版を1画面に縮める決定ではない。試作実装の開始は別途ユーザーの指示を待つ。

現時点で多数の敵、広いオープンワールド、複数の物語分岐を初版の必須要件には入れない。後から追加する場合は、この作品の核が伝わるかと制作量を見直す。

## 4. 機能要件

優先度は **必須候補**／**追加候補**を基本とする。D-16〜18で採用したF-06、A-03、A-07とG-02の記憶復元方法は確定事項として示す。ほかの候補は本書の承認まで設計案であり、実装を確約するものではない。

### 4.1 狐とステルス

| ID | 優先度 | 要件案 | 受け入れ時に見ること |
| --- | --- | --- | --- |
| F-01 | 必須候補 | 子狐を移動させ、伏せる・走る・尾で足跡を払う・近くの物に触れる行動を使える | どの行動が可能か画面で分かり、操作に直ちに反応する |
| F-02 | 必須候補 | 雪に足跡が残り、古さや風で変化し、尾で近くの跡を消せる | 狐が通った痕跡と消した結果をプレイヤーが目で追える |
| F-03 | 必須候補 | 鈴・枝など、狛犬が聞ける音を作れる | 音源・届いた範囲・狛犬の反応の関係が理解できる |
| F-04 | 必須候補 | 灯籠を取る・運ぶ・置くことができ、運搬中は周囲が明るくなる | 盗難の前後で隠れ方とルート選びが変わる |
| F-05 | 必須候補 | 発見・捕獲時に理由が分かり、やり直せる | 不可解な即時失敗や長い再プレイを強いられない |
| F-06 | 確定（D-16） | 子狐は伏せて倒木の下を通り、鳥居と別の経路で神社へ出入りできる。山犬は倒木の下を通れないが迂回できる | 小さな体が攻略と見た目の両方に意味を持ち、両経路が行き帰りに使える |

### 4.2 狛犬とJev

| ID | 優先度 | 要件案 | 受け入れ時に見ること |
| --- | --- | --- | --- |
| A-01 | 必須候補 | 狛犬は**自身が見聞きした事実とゲーム内で得た記憶**だけを使って判断する | 見ていない狐の現在地や巣の位置を理由に追跡しない |
| A-02 | 必須候補 | 性格を一貫して持つ。「任務に忠実で慎重、幼い動物には情がある」を初期案とする | 鈴だけでは安易に持ち場を離れず、複数の手掛かりや盗難で対応が変わる |
| A-03 | 確定（D-17） | Jevは狛犬の固定した性格から定める行動傾向と、実際の観測・記憶に沿って、その場で可能な行動意図を一つ選ぶ。確率を使った抽選はしない。視界・移動・当たり判定・捕獲はゲーム側が扱う | 選択を手掛かりと性格で説明でき、不可能な行動や盤面外の知識が反映されない |
| A-04 | 必須候補 | 狛犬の注目先を、視線・耳・姿勢・足音などで知らせる | プレイヤーが行動開始前に予兆を読める |
| A-05 | 必須候補 | Jevの応答待ちや短い通信障害で操作・描画を止めない | 一時的な通信不能では狛犬が定義済みのローカル行動を取る |
| A-06 | 追加候補 | プレイ後、狛犬が得た手掛かりと選んだ行動の短い記録を見られる | 「AIだから」ではなく判断の理由を振り返れる |
| A-07 | 確定（D-17）、詳細は検証 | 狛犬が新しい手掛かりを得る、見失う、調査が終わるなど、判断に意味のある状態変化でJevへ問い合わせる。同じ状態を毎秒再判断しない | 契機の抜け・重複、体感品質・遅延・利用量を測り、細かなまとめ方を調整する |
| A-08 | 必須候補 | 守り手は定位置で石像、持ち場を離れる時は動物の姿になり、役目を終えたら戻って石になる。変化は行動判断の予兆として見せる | 鈴だけで無条件に変化せず、いつ動き出すかをプレイヤーが読める。石像と動物が同じ一体に見える |

当初の「毎秒AIを使う」は検討の出発点だった。D-17では意味のある状態変化で問い合わせる方式を採用した。正確な連続観測のまとめ方と待機期限は検証する。Jevの[Choice](https://docs.typesafe.ai/primitives/choice)で候補を定義し、[State](https://docs.typesafe.ai/concepts/state)に性格・行動傾向・観測・記憶を分けて渡す。Choiceの返答には確率値も含まれるが、**ゲームは確率抽選をしない**。性格と判断が一貫するかは固定盤面で検証する。[Jev設計の詳細](komainu-jev.md)。

性格を示すための状況依存の判断はJevに担当させ、狐の座標を知る処理、経路探索、捕獲成立、物語の必須場面はゲームのルールとして扱う。プレイヤーにとっての公平さと、同じ入力を再現して検証できることを優先する。判断候補と送信する状態の具体的な項目は、後続の`komainu-jev.md`で定める。

### 4.4 プレイの流れと保存

| ID | 優先度 | 要件案 | 受け入れ時に見ること |
| --- | --- | --- | --- |
| G-01 | 必須候補 | 新規プレイから冒頭、探索、盗難、帰路、結末まで進める | 途中で目的を失わず、巣から神社への往復が一つのゲームとして成立する |
| G-02 | 必須候補、記憶復元は確定（D-18） | 捕獲・失敗時に安全なCP-B／Cからやり直す。狛犬の観測・記憶はCPの保存時点へ戻し、失敗した挑戦の記憶は持ち越さない | 狐・灯籠・足跡・狛犬の位置・姿・観測・記憶が一組で復元され、短い操作で再挑戦できる |
| G-03 | 必須候補 | ポーズ、操作説明、再開、終了を行える | プレイの中断と再開が迷わずできる |
| G-04 | 追加候補 | シーン間の進行を保存し、後日続きから再開できる | セーブとロード後に狛犬の観測・記憶・姿、灯籠の状態が矛盾しない |

G-04のセーブ範囲はプレイ時間と配布形態に依存するため未決定。D-18は**同一プレイ中の捕獲後の再挑戦**についての決定で、アプリ終了後の続きからの再開とは別の要件として扱う。

## 6. 受け入れ場面と確認方法

数値基準は対象PCと試作結果が決まってから設定する。ここでは**観察できる成功条件**を先に定義する。

| 場面 | 対応要件 | 確認すること |
| --- | --- | --- |
| 冒頭で巣から出る | E-01、P-01、G-01 | 初見の人が、弟妹を温めるために灯籠へ向かうことを説明できる |
| 開始後5〜10分に到達する | P-07、E-03、E-04 | 最初の狛犬との駆け引きに到達し、狛犬が状況に応じて判断する価値を体験できる |
| 足跡と鈴を別々に使う | F-02、F-03、A-01～04 | 狛犬は実際に得た手掛かりだけで動き、何に注目したか見た目と音で分かる |
| 同じ囮を繰り返す | E-03、A-02、A-07 | 狛犬が空振りを経験していた場合だけ判断の変化が起こり、性格と矛盾しない |
| 灯籠を取り、森へ戻る | F-04、P-04、G-01 | 神社が暗くなり、狐の持つ灯りで帰路の隠れ方と狛犬の判断が変わる |
| 狛犬に捕まる | F-05、G-02 | 発見原因をプレイヤーが理解でき、少ない手順で再挑戦できる |
| Jevが遅い／切断される | A-05、N-02、N-03 | 短い障害の間も操作・描画が続き、狛犬が定義された代替行動を取り、復旧時に矛盾する古い指示を実行しない |
| 巣へ戻り、結末に至る | P-05、G-01 | 狛犬がそれまで知らなかった弟妹の状態を実際に見てから行動し、結末までの因果が通る |
| 実際の表示サイズで画面を見る | E-02、E-05、P-02～04、N-01、N-09 | 子狐が愛らしく見え、狛犬・灯籠・足跡・右下の行動が読み取れる |

これらを正式な合否基準にする時は、対象者・評価人数・使用PC・観察記録の方法を`verification.md`で決める。

## 8. 技術方式は要件確定後に選ぶ

高品質な3Dモデルを使いながら固定視点の画面として仕上げるため、調査では **Blenderで素材を制作し、C++ + raylibで2.5D表示する方式**を第一候補にした。[制作方式の調査](../research/production/README.md)。ただし、これは機能要件ではなく実現手段。動く灯籠の光とキャラクターが自然に馴染むかは未検証であり、方式を確定していない。C++・Python・Javaの役割も、対象OSと配布条件を決めてから確定する。

Jevの実API呼び出しには接続条件とAPIキーが必要。今の段階ではキーを取得・入力することを要件にしない。GitHubで公開する範囲を決めた後、公開リポジトリに秘密情報を含めない接続方法を設計する。通信を必要とする完成版であっても、開発用の固定盤面や短い通信障害の確認にはローカルの代替判断を用意する。

## 9. 進める順番

1. **ゲームと物語:** 巣から神社までの具体的な場面、四つの行動、失敗時の扱い、5〜10分以内の見せ場を決める。全編の長さはそこから考える。
2. **狛犬の理想像:** どの手掛かりでどう迷い、何を学習ではなく記憶し、どう演技するかを先に設計する。その後にJev使用量と費用を見積もる。
3. **見た目と操作:** 画風の基準画像、狐・狛犬・灯籠の形、右下のHUDを決める。画像の生成は別途ユーザーの指示に従う。
4. **基本設計:** 描画方式、画面構成、Jev接続、長時間障害時の扱いを決める。
5. **検証:** プレイヤー体験、品質、Windowsでの性能、API遅延と費用の基準を定める。
